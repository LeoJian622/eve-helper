## User Scenarios & Testing *(mandatory)*

### User Story 1 - 后台任务身份跨用户隔离 (Priority: P1)

作为已登录用户,我触发的后台任务(以及系统定时任务)绝不能以其他用户的身份执行,我的身份也不应残留在之后被其他用户任务复用的工作线程上。否则用户 A 的数据操作可能以用户 B 的授权上下文执行,造成跨用户数据泄漏或行为归属错乱。

**Why this priority**: 这是 007 评审遗留项中唯一直接构成**跨用户机密性/完整性破坏**的缺陷(而非侦察面或卫生问题),影响面覆盖所有经线程池执行的后台任务路径。评审定性为既存缺陷,与 007 无关但相邻。

**Independent Test**: 在测试环境让两个用户的任务先后进入同一复用的工作线程,验证后者读不到前者的身份残留;交付「跨用户身份泄漏面消除」的价值。

**Acceptance Scenarios**:

1. **Given** 某工作线程刚执行完用户 A 的任务,**When** 执行用户 B 的无身份需求任务,**Then** 该任务观察到空身份,读不到用户 A 的任何认证信息
2. **Given** 某任务需要以提交者身份执行,**When** 任务结束(无论成功或失败),**Then** 工作线程上的身份被完全清理
3. **Given** 不属于任何用户的定时/调度任务,**When** 执行,**Then** 以匿名身份进行,不从执行环境继承任何身份

---

### User Story 2 - 登录端点不可枚举 (Priority: P2)

作为系统所有者,登录失败响应不得向外界泄露「账号是否存在」「距离锁定还剩几次」,使攻击者无法通过批量撞库请求先筛出有效账号清单、再针对性爆破,也无法探知锁定状态。

**Why this priority**: 对外直接可利用的侦察面(枚举有效账号 + 探知锁定状态),是后续凭证攻击的前置条件;但需后续爆破才构成实际入侵,故列 P1 之后。与 007 在 token 通路上「统一错误码防原因区分」是同类问题的相反做法,修复后两通路姿态一致。

**Independent Test**: 分别以「已注册账号 + 错误口令」和「未注册账号 + 任意口令」请求登录,比对客户端可见响应的全部内容;交付「登录失败零信息泄漏」的价值。

**Acceptance Scenarios**:

1. **Given** 账号存在但口令错误,**When** 登录失败,**Then** 响应为统一措辞,不含失败原因区分
2. **Given** 账号不存在,**When** 登录失败,**Then** 响应与场景 1 在状态码与消息内容上 100% 一致(亦不含剩余尝试次数)
3. **Given** 任一登录失败,**When** 查看服务端日志,**Then** 能区分账号存在性与剩余尝试次数(仅供运维与告警使用)
4. **Given** 任一登录失败,**When** 检查响应内容,**Then** 不含任何内部异常信息回显

---

### User Story 3 - 安全卫生项批量整治 (Priority: P3)

作为维护者,将 007 两份评审核定的 12 条 LOW 项一次性修复:token 响应的响应头姿态(通配跨源读取声明、缓存级别)、未认证端点的输入边界与日志注入、孤立密钥材料清理、运维命令的凭证暴露面、密钥库加载与响应写出工具内的代码卫生(死代码重载、与常量漂移的文案、方法间编码不一致),消除低危但持续负债的攻击面。

**Why this priority**: 单项危害有限、无已知可直接利用的链条,归为 polish;集中修复以避免同一批文件被反复打开评审。

**Independent Test**: 逐条按评审记录的「位置/问题」复现原状态并验证已修复;交付「007 评审 LOW 项零遗留」的价值。

**Acceptance Scenarios**:

1. **Given** 携带 token 的响应,**When** 检查响应头,**Then** 不含允许任意源跨源读取的声明,且缓存策略为不落地存储级别
2. **Given** 超长或畸形的刷新凭证输入,**When** 提交到未认证的刷新端点,**Then** 在边界处被拒绝,且因此产生的日志中无控制字符注入的伪造条目
3. **Given** 版本控制中孤立的公钥文件,**When** 全仓确认无引用,**Then** 从版本控制移除(不改写历史)
4. **Given** 运维文档中的审计/清理命令,**When** 按文档执行,**Then** 凭证不出现在进程列表或 shell 历史中
5. **Given** 密钥库加载与响应写出工具,**When** 检视,**Then** 无易误用的死代码路径、无与常量取值漂移的提示文案、同类方法行为一致

---

### Edge Cases

- 取消身份继承后,现有依赖「继承到的身份」的后台任务(若存在)将失去上下文 —— 计划阶段必须审计全部任务提交点,逐一改为显式传播或显式匿名,不得静默失上下文
- 登录失败消息统一后,合法用户无法自行区分「输错用户名」与「输错口令」,细节仅存服务端日志(接受的权衡)
- 「剩余尝试次数」展示取消后,账号被锁定场景的对外表现与平常失败完全一致
- 孤立公钥文件的移除须先经全仓引用确认与用户确认;该文件是公钥非秘密,仅移除当前版本,不改写 git 历史
- 刷新凭证输入的长度上限须兼容合法凭证实际格式(UUID),拒绝异常长度而不误伤正常请求
- 日志脱敏的控制字符剔除不得破坏既有日志消费方(告警规则、取证流程)的解析假设

## Requirements *(mandatory)*

### Functional Requirements

**US1(跨用户身份隔离)**

- **FR-001**: 系统必须保证被池化/复用的工作线程在执行任何新任务前,不携带来自先前任务或提交线程的用户身份
- **FR-002**: 后台任务确需以提交者身份执行时,身份必须显式传播给该任务,并在任务结束时(无论成败)完全清理
- **FR-003**: 不需要用户身份的后台/定时任务必须以匿名身份执行,不从执行环境继承任何身份

**US2(登录不可枚举)**

- **FR-004**: 所有凭证类登录失败(账号不存在、口令错误、账号锁定等)必须向客户端返回统一错误消息,不可区分失败原因
- **FR-005**: 登录失败的细节(账号存在性、剩余尝试次数)必须仅记录于服务端日志,不得返回客户端
- **FR-006**: 登录失败响应不得回显任何内部异常信息

**US3(卫生项整治)**

- **FR-007**: 携带 token 的响应不得声明允许任意源跨源读取,缓存策略必须为不落地存储级别
- **FR-008**: 未认证端点的刷新凭证输入必须有长度与格式边界校验;日志中输出的任何经脱敏的外部输入必须对控制字符注入免疫
- **FR-009**: 确认无引用后,必须从版本控制移除孤立的公钥文件
- **FR-010**: 运维文档中的命令示例不得使凭证暴露于进程列表或 shell 历史
- **FR-011**: 密钥库加载工具必须消除无调用方的易误用重载、自抛自捕分支,以及与常量取值漂移的硬编码文案
- **FR-012**: 同一响应写出工具内的各方法,字符编码行为必须一致

### Key Entities

本 feature 为行为加固,不新增数据实体。涉及的行为对象:

- **登录失败响应**: 对外统一措辞 + 对内细节留痕的双通道
- **任务身份上下文**: 工作线程上可被读取的用户身份,其生命周期(传播/清理)由本 feature 重新约束

## Success Criteria *(mandatory)*

- **SC-001**: 「已注册账号 + 错误口令」与「未注册账号 + 任意口令」的登录失败响应成对比对 100% 一致(消息、状态码全字段),枚举攻击获得零信息
- **SC-002**: 回归测试覆盖项目全部后台任务提交入口:复用工作线程执行新任务前身份恒为空、任务结束后身份恒为空,通过率 100%
- **SC-003**: 12 条 LOW 项逐条对照评审记录建议处置完成,自检记录归档 `docs/reviews/`
- **SC-004**: 全量测试回归零新增失败用例(Failures 段逐名 diff,基线环境性失败不计)
- **SC-005**: 变更代码行覆盖率 ≥ 80%
- **SC-006**: 独立安全复审结论零 CRITICAL/HIGH

## Assumptions

- 全部缺陷均为 007 两份评审(2026-08-12 java-reviewer / security-reviewer)核定的**既存缺陷**,非 007 引入;本 feature 只做修复,不新增业务功能
- **排除项**:LOW-6(java)已由 007 T040 修复;LOW-8(java)升级为 HIGH-2 且实际生产 profile 文件由用户管理(不入库),属部署侧动作 —— 二者不在本 feature 范围
- 技术栈冻结(宪法第四条),全部修复在既有依赖内完成,不引入新库
- 登录限流/尝试次数统计机制本身保留,仅改变其对外呈现方式
- 登录与刷新端点的既有接口契约(HTTP 状态码、响应顶层结构)对外不变,仅消息内容与响应头变化
- 评审记录(`docs/reviews/2026-08-12-007-*.md`)与各缺陷位置的详细论证作为本 spec 的输入事实来源
