# Feature Specification: ESI 数据 × 系统用户强关联

**Feature Branch**: `014-esi-data-user-binding`
**Created**: 2026-08-19
**Status**: Draft
**Input**: User description: "ESI 获得的数据除了跟角色/军团/联盟关联，还要与用户做关联，避免其他用户越权访问。"

## 背景与目标

系统从 EVE Online ESI 同步了多类数据（角色资产、钱包流水、蓝图、工业任务、月矿开采、军团建筑）。这些数据当前只按 EVE 维度（角色 ID / 军团 ID）标识，导致任何"知道该角色或军团 ID 的人"都能读取这些数据——即便数据并非他同步、也不属于他。这构成越权访问（IDOR）风险。

本特性引入**系统用户归属**：每份 ESI 数据明确归属到同步它的那个系统用户，读取时只对该用户（及其管理域）可见。数据从"军团成员共享"收紧为"同步者私有"，从根源阻断越权。

## User Scenarios & Testing

### User Story 1 - 人物数据只对自己可见 (Priority: P1)

玩家甲同步过某角色的资产与钱包流水。玩家乙若知道该角色 ID，当前能读到甲的资产与流水；同步后**乙无法读到**，只有甲（以及其管理域）能看。

**Why this priority**: 人物维度数据天然属于单一角色属主，是最清晰、最优先要收紧的越权点，且改动路径独立、可先行验证。

**Independent Test**: 创建甲、乙两个用户，甲持有角色 A，乙仅登录不持有。调用角色 A 的数据接口，甲可见、乙被拒，且乙收到的拒绝消息不泄露数据是否存在。

**Acceptance Scenarios**:

1. **Given** 甲持有角色 A 且已同步其资产、**When** 甲查询角色 A 的数据，**Then** 返回完整数据
2. **Given** 乙未持有角色 A，**When** 乙查询角色 A 的数据，**Then** 请求被拒绝，且响应不泄露角色 A 有多少数据
3. **Given** 甲、乙两用户都持有同一角色 A，**When** 两人各自查询角色 A 的数据，**Then** 两人都可见（同一角色属主共享）

---

### User Story 2 - 军团数据只对自己同步的部分可见 (Priority: P1)

玩家甲和乙都在同一军团。当前两人都能看到该军团全部钱包/建筑数据；同步后——**只有"实际同步过该军团的人"可看到自己同步的数据**，同团但未同步的成员不可见，阻断"用一个小号身份加入军团即可读取全团数据"的越权路径。

**Why this priority**: 这是本次要推翻的核心语义（军团共享 → 同步者私有），是用户最强诉求，涉及面最广（钱包/建筑/月矿等军团维度数据）。

**Independent Test**: 甲、乙同团。甲同步过军团钱包，乙从未同步。调用军团钱包接口：甲可见，乙被拒。乙即使提供了正确的军团 ID 也拿不到任何数据。

**Acceptance Scenarios**:

1. **Given** 甲同步过某军团的金融/建筑数据，**When** 甲查询该军团数据，**Then** 返回甲同步范围内的数据
2. **Given** 乙与该军团同属但从未同步它，**When** 乙查询该军团数据，**Then** 请求被拒绝
3. **Given** 同一军团的数据曾被多人各自同步，**When** 其中一人查询，**Then** 只返回该同步者本人同步的部分，不并入他人数据

---

### User Story 3 - 系统管理域可见全部数据 (Priority: P2)

系统管理员需要查看全量数据以支撑运维、排查与审计；管理域的越权探测应被放行。

**Why this priority**: 管理域的豁免是保证系统可运维的必要能力，但它应是少数账户的特权，须与普通用户的私有约束隔离。

**Independent Test**: 以系统管理域身份调用任意角色/军团数据接口，均返回完整数据；普通用户则保持私有约束。以此为对照验证普通用户的越权拦截确实生效。

**Acceptance Scenarios**:

1. **Given** 系统管理域用户，**When** 查询任意已同步的角色或军团数据，**Then** 返回完整数据
2. **Given** 普通用户（非管理域），**When** 查询非自己属主的数据，**Then** 被拒绝（管理域豁免不扩散到普通用户）

---

### User Story 4 - 存量数据获得正确归属 (Priority: P2)

特性上线前已有的历史数据没有归属记录。迁移后：人物维度数据归属到其角色属主；军团维度历史数据归属到系统管理域（因无法唯一判定原始同步者，避免误归给某个人）。上线后数据不丢失、不被错误私有化。

**Why this priority**: 存量迁移决定既有用户是否还能看到自己的历史数据，是平滑上线的前提，属于不可跳过的收尾项。

**Independent Test**: 迁移前对人物与军团的存量行各抽样；迁移后验证人物行归属到角色属主、军团行归属到管理域，行数不发生丢失。

**Acceptance Scenarios**:

1. **Given** 存量人物数据行，**When** 执行迁移，**Then** 每行归属到其角色属主，属主查询可见
2. **Given** 存量军团数据行（无法唯一判定原始同步者），**When** 执行迁移，**Then** 归属到系统管理域，普通用户不可见，避免误私有化
3. **Given** 迁移过程，**When** 任意时间点核对，**Then** 数据行总数不减少（不丢失任何历史数据）

---

### Edge Cases

- 同一角色被多个用户持有：该角色数据对所有这些属主可见（角色共享，不切分）。
- 同一军团数据被多人各自同步：各人只见自己同步的部分，不合并、不串扰。
- 角色退团 / 所属军团变化：历史军团数据仍归属到当时实际同步它的用户，不因退团而转移或失效。
- 用户被删除或禁用：其名下数据的归属与可见性需明确定义（本特征预设：随用户处理策略，不做数据二次分配，见 Assumptions）。
- 系统管理域的受控使用：管理域豁免必须是少数特权账户，普通登录状态一律按私有约束对外。
- 联盟维度预留：支持以联盟为 EVE 归属维度进行校验，但当前无联盟级数据资源，仅为机制预留。

## Requirements

### Functional Requirements

- **FR-001**: 系统 MUST 在接收任何 ESI 数据时记录其归属的系统用户。
- **FR-002**: 人物维度的数据读取 MUST 仅返回当前请求用户所属角色的数据；未持有该角色的用户 MUST 被拒绝。
- **FR-003**: 军团维度的数据读取 MUST 仅返回当前请求用户实际同步过的数据；同团但未同步的成员 MUST 被拒绝（推翻军团成员共享）。
- **FR-004**: 同一角色被多用户持有时 MUST 对该角色的全部属主共享返回（不切分）。
- **FR-005**: 系统 MUST 支持按人物 / 军团 / 联盟 三种 EVE 维度进行归属判定。
- **FR-006**: 系统管理域 MUST 可访问全部数据且不受私有约束限制。
- **FR-007**: 越权访问的拒绝响应 MUST 不泄露目标数据是否存在或规模（避免构造枚举探测）。
- **FR-008**: 系统 MUST 提供一次性迁移，为既有历史数据补齐归属：人物维度归属角色属主、军团维度归属管理域，且数据行总数不得减少。

### Key Entities

- **系统用户（User）**：登录与授权的账户主体，是数据归属的最终所有者。
- **EVE 角色（Character）**：包含角色 ID、所属军团 ID、所属联盟 ID；一个角色可绑定到多名系统用户。
- **ESI 数据（Character Assets / Wallet Journal / Blueprints / Industry Jobs / Mining Detail / Structures / Observations）**：从 ESI 同步的业务数据，每种标识其 EVE 来源（人物或军团），并归属到同步它的系统用户。
- **EVE 归属维度**：角色（Character）、军团（Corporation）、联盟（Alliance），作为判定"数据属于哪个 EVE 主体"的三种口径。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 普通用户对非属主数据的访问在接口层 100% 被拒绝。
- **SC-002**: 越权访问的拒绝响应不包含任何暗示目标数据存在性的细节（数据条数、金额、时间）。
- **SC-003**: 同一军团内未同步该军团的成员，对军团数据的访问 100% 被拒绝。
- **SC-004**: 存量数据迁移后行数不减少（0 丢失），人物维度 100% 归属到角色属主、军团维度 100% 归属到管理域。
- **SC-005**: 系统管理域可 100% 查询全部已同步数据，用于运维与审计。
- **SC-006**: 上线后无法通过"以敌对小号身份加入军团"的路径获得该军团任何私有数据。

### Code Quality Criteria

- **SC-007**: 新增/修改逻辑的单元测试覆盖率 ≥80%。
- **SC-008**: 人物私有、军团私有、管理域豁免、存量迁移四条用户旅程均有自动化测试覆盖。

## Assumptions

- 本特性面向私有部署为主的场景：数据归属收紧为同步者私有，接受"同军团多人各自同步时每人只见自己部分"的碎片化折衷（用户已明确拍板推翻军团共享）。
- 军团维度存量数据因无法唯一判定原始同步者，统一归属系统管理域；其后续可见性由产品/运营在管理域内安排，不做自动二次分配。
- 用户被删除/禁用时，其名下 ESI 数据的处理沿用系统既有的用户处理策略，本特性不引入新的数据接管规则。
- 联盟维度本特性仅补齐归属判定机制，不产出新的联盟级数据资源或读取端点。
- 电子数据（如 EVE 市场公开行情）不在本特性范围内，仅针对经用户操作的 ESI 业务数据。
