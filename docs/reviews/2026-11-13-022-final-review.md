**失败场景**:
- **(a) 系统军团归属振荡（主部署场景——spec 明示用户为军团全体成员，Director 必然存在）**: :00 QQ 写 user_id=1 → :05 APP 翻转为选角属主 → 既有 005 建筑端点私有化读（StructureMapper.xml:453-455,504-506 等 `s.user_id=#{userId}`）对该用户呈现「:05~:00 可见、:00~:05 不可见」的每小时振荡——**既有功能行为被 022 改变**。
- **(b) QQ 清理链路断裂 → 陈旧行永久化**: 建筑在 :00~:05 之间被拆除/unanchor 时，其行最后写入者为 APP（user_id=属主）→ QQ 下一轮 `selectByCorporationId(corpId, 1)` 永远看不到该行 → **永不删除** → `selectFuelExpiresList`（无 user 过滤、`fuel_expires IS NULL` 亦命中）永久匹配 → ① APP 侧每 24h 一条幽灵 FUEL_LOW（dedup 窗口滚动重置，违反 SC-007「不漏」之反面「不虚报」）；② **QQ 侧 18/22 点燃料推送同样读到幽灵行 → FR-018/SC-008「QQ 零行为变更」被数据层击穿**（首个建筑消失事件即触发，潜伏性）。
- **(c) 非系统军团零清理路径**: APP 同步为所有成员军团新建 structure 行（022 之前不存在），QQ 清理只覆盖系统军团 → 这些行一旦陈旧同样永久产生幽灵通知。

**定级理由**: 非安全漏洞、非即时数据丢失（潜伏至首个建筑 churn 事件），但违反两条硬约束的实质（014/QQ 零侵入在数据层被击穿）且必然随时间显现 → **Important（修复波必须项，建议与 IMP-1 同波；若拖延至生产运行后爆发，届时按 Critical 处置）**。

**修复建议（任选组合，推荐 i+ii）**:
- (i) APP 同步对 QQ 已覆盖的军团让位：`corpId` 属系统角色所在军团时跳过（QQ 每小时已同步，APP 重复写无增益，只带来翻转）；或改用不含 `user_id = values(user_id)` 的 upsert 变体（新增 mapper 语句，不动既有语句）。
- (ii) `AppStructureSyncService.syncOneCorp` 补 stale 清理：以 **corp 维度**（与燃料读路径同口径，不带 user 过滤）删除 `corporation_id=corpId AND structure_id NOT IN (新拉集合)` 的行，镜像 StructureService.java:143-150 语义。
- (iii) 兜底（最小改动）：`detectFuelLowForCorp` 对命中行校验「该 structureId 是否仍在最近一次同步的 ESI 集合中」成本较高，不推荐。

#### MIN-C: 燃料扇出在建筑循环内重复执行 + 任务上下文角色查询不缓存 → ESI 调用放大；与 600s 运行锁 TTL 相互作用

#### MIN-D: 30d 清理 SQL 无可用索引 + DELETE...LIMIT 无 ORDER BY

#### MIN-E: 团员追踪 corpId 未与绑定角色军团比对（纵深防御缺口，无实际泄露）
