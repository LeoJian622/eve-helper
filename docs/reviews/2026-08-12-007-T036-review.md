## 3. 对 6 个重点问题的判断

### Q1 移除延迟后是否留下功能空洞?

**部分是,但可接受,且已立项。**

L2 现退化为**纯观测**:`POST /auth/tokens` 事实上**没有任何应用层速率限制**。这是**有意的**,理由:

1. **原方案不是防护而是自伤**。延迟不降低攻击者吞吐(其用并发连接),只消耗我方线程 —— 净效果为负。
2. **真正的抗洪泛来自失败路径廉价性**,且实测确认存在:
   - 空 token 分支(`AuthApplicationService:109-111`)**直接抛出,连 Redis 都不碰** —— 最廉价路径
   - 格式非法分支:1 INCR + 1 EXPIRE = **2 次** Redis 往返
   - 随机 UUID 分支:1 GET + 1 INCR + 1 EXPIRE = **3 次** Redis 往返
   - 三者均**不触 DB、不触 token 生成、不触 RBAC**
3. **速率限制的正确位置是入口层**(反代/网关/`max-connections`),而非业务线程内自我阻塞。本次已把容量参数显式化,为入口层限流留出可审基线。

⚠️ **诚实表述**:这意味着 007 **没有**为 refresh 端点提供应用层限流。SC-015 的措辞已同步为「仅告警」,不再声称整形能力。**若日后需要真限流,必须在入口层或用 Servlet 异步实现,不得回退到工作线程阻塞。**

### Q2 `l2_noDelayConstantsRemain` 反射断言是否恰当?

**恰当,建议保留。明确判断,不含糊。**

支持理由:
1. **它抓的是设计意图残留,不是行为** —— 与计时断言互补而非重复。变异测试恰好证明了互补性:插回**字面量** `Thread.sleep(150L)` 时,计时断言 FAIL 而常量断言 PASS(因为没用常量)。反之若有人恢复常量却暂未接线,常量断言先响。
2. **不依赖计时** —— 慢机、CI 负载、GC 停顿都不影响它。这正是 Q3 的兜底。
3. **成本极低**,`getDeclaredFields()` 无副作用。

风险与缓解:
- ⚠️ 该断言**按字段名匹配**(`contains("DELAY")`),若日后有正当理由引入名含 DELAY 的字段(如 `MAX_DELAY_TOLERANCE_MS` 用于别的用途)会误报。**这是可接受的**:误报会强制开发者阅读注释、理解为何禁止延迟,属于**有益的摩擦**。
- 若未来确需放宽,应改为断言"无 `Thread.sleep` 字节码"而非字段名 —— 但那需要 ASM/字节码工具,当前不值得(YAGNI)。

### Q3 `elapsed < 80ms` 在慢机上是否假失败?

**风险存在但已被兜底,可接受。**

- 被测路径是**纯内存 + Mockito mock**,无 I/O、无网络。实测 0.087s 是**整个 7 用例测试类**的耗时,单用例远低于此。80ms 对纯内存操作是约 2~3 个数量级的余量。
- **真正的保险是 Q2 的常量断言**:即使极端负载下计时断言假失败,常量断言仍准确反映设计状态;反之若有人删掉计时断言,常量断言仍守住。两条断言**任一存活即可发现回退**。
- ⚠️ **未实测**:未在受限 CPU / 高负载 CI 环境验证。若日后出现零星假失败,**正确处置是放宽阈值(如 200ms)而非删除断言** —— 只要阈值远低于 100ms 的旧延迟下限即可保持鉴别力。已写入本记录供后人参考。

### Q4 Tomcat 参数值是否合理、放在公共配置是否恰当?

**值合理;位置恰当但有已知局限。**

- `threads.max=200` / `min-spare=10` / `max-connections=8192` **即 Boot 默认值**,显式写出的目的是**可见可审**,不改变现有行为 —— 这一点很重要:本次改动**不引入容量行为变更**,零回归风险。
- `accept-count=100` 也是 Boot 默认值。队满即拒新连接,快速失败优于无界排队。
- **放在入库的 `application.yml`**:该文件不含凭证(全为 `${ENV_VAR}` 占位符),是公共基线的正确位置。
- ⚠️ **已知局限(与 whiteUrlList 同型)**:`server.tomcat.*` 是标量属性,profile 文件若声明同名键会**覆盖**公共值。我**无法核验** `application-{ali,aliw,prod}.yml` 是否覆盖了这些键(读凭证文件被安全策略正确阻止)。**未实测**,已记入下方遗留项。
- ✅ **绑定已验证**:`@SpringBootTest` 6/6 通过。键名拼错会 `Failed to bind`,故绑定正确。

### Q5 `MeterRegistry` 出现在 domain 层是否违反 DDD?

**技术上不违反本项目的分层规则,但气味可疑。**

- 实测 `grep -rn 'import xyz.foolcat.eve.evehelper.(application|infrastructure|interfaces)' domain/` **无输出** —— domain 层不依赖任何上层,依赖规则未破。
- micrometer 是**第三方可观测库**,类似 slf4j(`@Slf4j` 也在 domain 层遍布),按本项目既有惯例可接受。
- ⚠️ **但**:严格 DDD 会认为"指标上报"是基础设施关切,应通过 `domain.port.metrics.MetricsGateway` 端口抽象(与既有 `CacheGateway`/`EsiGateway` 一致)。**当前不改**:T037 要重新裁决告警通路方案,若改为结构化日志则 `MeterRegistry` 可能整体移除,现在抽端口有返工风险。**已记入 T037 一并裁决。**
